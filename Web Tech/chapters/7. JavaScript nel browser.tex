\chapter{JavaScript nel browser}

Finora abbiamo studiato il \textbf{linguaggio} JavaScript. Il linguaggio però
può essere eseguito in \textbf{ambienti ospite} (\textit{host environment})
diversi:

\begin{itemize}
  \item i \term{web browser}, per i quali JavaScript è stato originariamente
        creato;
  \item i \term{web server}, per esempio tramite il runtime Node.js.
\end{itemize}

Ogni ambiente ospite fornisce oggetti e funzioni \textbf{propri}, in aggiunta a
quelli inclusi nel nucleo del linguaggio. In questo capitolo studiamo l'ambiente
del browser.

\subsection{L'oggetto window}

L'ambiente del browser ha un oggetto \guillemotleft radice\guillemotright\ chiamato \term{window},
che svolge due ruoli:

\begin{enumerate}
  \item è l'\textbf{oggetto globale} per il codice JavaScript;
  \item rappresenta la \textbf{finestra del browser} e fornisce i metodi per
        controllarla.
\end{enumerate}

Le funzioni dichiarate a livello globale (e le variabili dichiarate con
\code{var}) diventano proprietà dell'oggetto \code{window}.

\begin{affianco}[0.55][c]
\begin{lstlisting}[style=js, name=window.js]
let msg = "Hello!";

function greet(name) {
  console.log(`${msg}, ${name}!`);
}

greet("Web Technologies");       // Hello, Web Technologies!
window.greet("window object");   // Hello, window object!
\end{lstlisting}
\risultato
\begin{immagine}[\code{greet} è una proprietà di \code{window};\\
                 \code{msg}, dichiarata con \code{let}, no.]
\begin{tikzpicture}
  \mchiave{1.4cm}
  \oggetto{w}{(0,0)}{3.0cm}{window}
    {greet/function, document/\ldots, location/\ldots, \ldots/}
  \variabile{m}{(0.45,-3.3)}{msg}{"Hello!"}
  \scopo{1}{g}{let e const globali}{(m)(m-nome)}
  \node[mnota, anchor=west, text=merr] at ([xshift=4pt]g.east)
    {\code{window.msg}\\ vale \code{undefined}};
\end{tikzpicture}
\end{immagine}
\end{affianco}

Le variabili dichiarate con \code{let} e \code{const} sono anch'esse globali,
ma vivono in uno scope separato e \textbf{non} diventano proprietà di
\code{window}: \code{window.msg} vale \code{undefined}.

\subsection{Il DOM e il BOM}

Il \term{DOM} (\textit{Document Object Model}) rappresenta il contenuto del
documento corrente. L'oggetto \code{document} è il punto d'ingresso principale
alla pagina e fornisce i modi per accedere ai contenuti e modificarli.

\begin{affianco}[0.6][c]
\begin{lstlisting}[style=html, name=dom-primo.html]
<body>
  <p>Hello!</p>
  <script>
    document.body.style.background = "pink";
    document.querySelector("p").innerText = "Hello DOM!";
  </script>
</body>
\end{lstlisting}
\risultato
\begin{browser}[dom-primo.html]
  \vspace*{-6pt}\noindent\makebox[\linewidth][l]{\hspace*{-8pt}%
  \colorbox{css-pink}{\makebox[\dimexpr\linewidth+16pt-2\fboxsep][l]{%
    \rule[-14pt]{0pt}{36pt}Hello DOM!}}}\vspace*{-6pt}
\end{browser}
\wtnota{Sfondo rosa e testo cambiato: il DOM\\ è stato modificato dallo script.}
\end{affianco}

Il \term{BOM} (\textit{Browser Object Model}) comprende invece gli oggetti
aggiuntivi forniti dal browser per lavorare \textbf{con il browser stesso},
non con il contenuto del documento.

\begin{lstlisting}[style=js, name=bom.js]
// location contiene informazioni sulla URL del documento corrente
console.log(location.href);        // http://localhost:3000/07-JavaScript...

// screen contiene informazioni sul display usato dall'utente
console.log(screen.availWidth);    // 2048

// navigator contiene dettagli sul browser e sulla piattaforma
console.log(navigator.userAgent);  // Mozilla/5.0 (Windows NT 10.0...

// history rappresenta la cronologia di navigazione
history.back();                    // come premere "indietro" nel browser
\end{lstlisting}

\section{Il DOM}

Quando abbiamo studiato i selettori CSS avevamo accennato al fatto che i
documenti HTML si possono vedere come \textbf{alberi}: parlavamo di discendenti,
figli, fratelli. Il DOM \textbf{formalizza} quell'intuizione.

\begin{itemize}
  \item Ogni tag HTML è un oggetto nel DOM.
  \item I tag annidati sono \textbf{figli} di quelli che li racchiudono.
  \item Anche il \textbf{contenuto testuale} di un tag è un oggetto, ed è figlio
        del tag.
  \item Gli \textbf{attributi} di un tag sono accessibili come proprietà
        dell'oggetto corrispondente.
\end{itemize}

La radice dell'albero è il nodo \code{document}; sotto di lui c'è l'elemento
\tg{html}, e da lì tutti gli altri. Si noti che il testo (\guillemotleft Exam\guillemotright,
\guillemotleft 30\guillemotright\ldots) non è una proprietà del tag che lo
contiene, ma un \textbf{nodo a sé}, figlio di quel tag.

\subsection{Spazi e a-capo: i nodi di testo che non si vedono}

La figura è una semplificazione. Quando scriviamo HTML andiamo a capo e
indentiamo i tag per renderlo leggibile: quegli a-capo e quelle indentazioni sono
caratteri come tutti gli altri, e il browser li conserva nel DOM come
\textbf{nodi di testo}, anche se poi non li mostra.

Nella console e nei disegni questi caratteri invisibili si scrivono con le
sequenze di escape delle stringhe JavaScript:

\begin{itemize}
  \item \code{\textbackslash n} è il carattere \textbf{a capo}
        (\textit{newline}), quello che si inserisce premendo Invio;
  \item \code{\textbackslash t} è la \textbf{tabulazione} (\textit{tab}), quella
        che si inserisce premendo Tab per indentare. Se il file è indentato con
        gli spazi, al suo posto ci sono degli spazi: nei disegni scriviamo
        comunque \code{\textbackslash t} per dire \guillemotleft l'indentazione\guillemotright.
\end{itemize}

Un nodo \code{\#text \textbackslash n\textbackslash t}, quindi, è il testo che
si trova fra la fine di un tag e l'inizio del successivo: un a-capo seguito
dall'indentazione della riga dopo.

\begin{affianco}[0.42][c]
\begin{lstlisting}[style=html, name=spazi.html]
<!DOCTYPE html>
<html>
  <head><meta charset="utf-8">
    <title>JavaScript</title>
  </head>
  <body>
    <p>Hello!</p>
  </body>
</html>
\end{lstlisting}
\risultato

seguito da un nodo di testo fatto solo di spazi. Per brevità questi nodi vengono
di norma omessi nei disegni (in questa dispensa li mostriamo quando contano),
ma esistono sempre: è il motivo per cui \code{document.body.firstChild} molto
spesso non è l'elemento che ci si aspetta, ma un nodo di testo che contiene
\code{"\textbackslash n\textbackslash t"}. Lo vedremo bene quando impareremo a
navigare l'albero.

\section{Trovare elementi}

L'oggetto \code{document} fornisce diversi metodi per selezionare elementi.

\begin{affianco}[0.62][c]
\codicepiccolo
\begin{lstlisting}[style=html, name=trova.html]
<ul>
  <li id="a">A</li>
  <li class="foo bar">B</li>
  <li name="c">C</li>
</ul>
<script>
  console.log(document.getElementById("a"));
  console.log(document.getElementsByClassName("foo"));  // HTMLCollection (1)
  console.log(document.getElementsByName("c"));         // NodeList (1)
  console.log(document.getElementsByTagName("li"));     // HTMLCollection (3)
</script>
\end{lstlisting}
\risultato
\begin{console}
<li id="a">A</li>
HTMLCollection [ li.foo.bar ]
NodeList [ li ]
HTMLCollection(3) [ li#a,
  li.foo.bar, li ]
\end{console}
\end{affianco}

I metodi \code{querySelector(css)} e \code{querySelectorAll(css)} sono i più
versatili, perché prendono in ingresso un \textbf{selettore CSS}: tutto ciò che
abbiamo imparato nel capitolo sui CSS torna utile qui.

\begin{itemize}
  \item \code{querySelector} restituisce solo il \textbf{primo} elemento che
        corrisponde al selettore;
  \item \code{querySelectorAll} restituisce una \textbf{lista} di
        corrispondenze;
  \item tutti i metodi restituiscono \code{null} quando non trovano nulla.
\end{itemize}

\begin{affianco}[0.62][c]
\codicepiccolo
\begin{lstlisting}[style=html, name=queryselector.html]
<ul>
  <li id="a">A</li> <li class="foo bar">B</li> <li name="c">C</li>
</ul>
<script>
  console.log(document.querySelector("ul > li"));         // primo <li>
  console.log(document.querySelectorAll("ul > li"));      // NodeList (3)
  console.log(document.querySelector("ul > li.myclass")); // null
</script>
\end{lstlisting}
\risultato
\begin{console}
<li id="a">A</li>
NodeList(3) [ li#a, li.foo.bar,
  li ]
null
\end{console}
\end{affianco}

\subsection{HTMLCollection e NodeList}

I metodi che possono trovare più elementi non restituiscono un array, ma una
\textbf{collezione}. Nelle stampe qui sopra ne compaiono due tipi diversi,
\code{HTMLCollection} e \code{NodeList}: vale la pena capire bene che cosa li
distingue.

\begin{affianco}[0.5][c]
\begin{itemize}
  \item Una \code{HTMLCollection} contiene \textbf{solo elementi} ed è sempre
        \term{viva}: riflette in ogni momento lo stato del documento.
  \item Una \code{NodeList} può contenere \textbf{nodi di qualunque tipo}
        (anche testo e commenti). Quella di \code{querySelectorAll} è
        \term{statica}: una fotografia del documento nel momento della ricerca.
\end{itemize}

Entrambe \textbf{somigliano} a un array: hanno la proprietà \code{length}, si
accede agli elementi con le parentesi quadre (\code{lista[0]}) e si possono
scorrere con \code{for...of}. Ma \textbf{non sono array}: non hanno \code{map},
\code{filter} e gli altri metodi visti nel capitolo 6. Quando servono, si
converte la collezione in un vero array con \code{Array.from(lista)} oppure con
lo spread, \code{[...lista]}.

\begin{esempio}{Una collezione che cambia da sola}

</script>

<a href="/">Second Link</a> <a href="/">Third Link</a>
<script>
  console.log(links);   // HTMLCollection (3), senza nuova ricerca!
</script>
\end{lstlisting}

\section{Navigare il DOM}

Gli elementi HTML più esterni sono disponibili anche come proprietà
dell'oggetto \code{document}:

\begin{itemize}
  \item \code{document.documentElement} per l'elemento \tg{html};
  \item \code{document.head} per l'elemento \tg{head};
  \item \code{document.body} per l'elemento \tg{body}.
\end{itemize}

In generale, ogni nodo del DOM contiene riferimenti al proprio
\textbf{genitore}, ai \textbf{fratelli} e ai \textbf{figli}, e seguendoli ci si
può spostare in tutto l'albero. Questi riferimenti sono in \textbf{sola
lettura}: servono a muoversi, non a cambiare la struttura.

\section{La gerarchia delle interfacce}

Ogni nodo del DOM è un oggetto JavaScript, e ogni oggetto ha un \textbf{tipo}:
un elemento \tg{input} è un \code{HTMLInputElement}, un nodo di testo è un
\code{Text}, il documento è un \code{Document}. Questi tipi si chiamano
\term{interfacce}, e sono organizzati in una \textbf{gerarchia di
ereditarietà}: ognuno eredita le proprietà e i metodi di quello sopra di lui, e
ne aggiunge di propri.

\begin{figure}[H]

\warning{Questo non è un albero DOM}{
  Il disegno somiglia a quelli dei paragrafi precedenti, ma dice tutt'altra

  pagina (\guillemotleft chi \textbf{contiene} chi\guillemotright), e cambia da
  una pagina all'altra. Questo albero descrive invece le \textbf{famiglie} di
  oggetti (\guillemotleft chi \textbf{è un tipo particolare di}
  chi\guillemotright), ed è lo stesso per qualunque pagina: il ramo fra
  \code{HTMLElement} e \code{HTMLInputElement} non vuol dire che un elemento
  contiene l'altro, ma che \textbf{ogni} \code{HTMLInputElement} \textbf{è
  anche} un \code{HTMLElement}. È la catena dei prototipi del capitolo 6, vista
  dall'alto.}

\subsection{Che cosa si eredita}

Un \tg{input} della pagina è quindi, contemporaneamente, un
\code{HTMLInputElement}, un \code{HTMLElement}, un \code{Element}, un
\code{Node} e un \code{EventTarget}, e ha \textbf{tutte} le proprietà di
ciascun livello. Per questo può essere usato ovunque ci si aspetti un
\code{Node}: ha tutto quello che ha un nodo, più molto altro.

\begin{affianco}[0.5][c]
\codicepiccolo
\begin{lstlisting}[style=html, name=gerarchia.html]
<input type="text" value="ciao">
<script>
  let input = document.querySelector("input");

  console.log(input instanceof HTMLInputElement); // true
  console.log(input instanceof HTMLElement);      // true
  console.log(input instanceof Element);          // true
  console.log(input instanceof Node);             // true
  console.log(input instanceof EventTarget);      // true
  console.log(input instanceof Text);             // false

  // proprieta' ereditate da livelli diversi
  console.log(input.value);     // ciao   (HTMLInputElement)
  console.log(input.tagName);   // INPUT  (Element)
  console.log(input.nodeName);  // INPUT  (Node)
</script>
\end{lstlisting}
\risultato
\begin{immagine}[Ogni livello aggiunge qualcosa;\\
                 l'\code{<input>} ha tutto, dall'alto in basso.]
\begin{tikzpicture}[

Vale anche il contrario: un oggetto ha \textbf{soltanto} le proprietà dei
livelli da cui discende. Un nodo di testo è un \code{Text}, che discende da
\code{CharacterData} e poi da \code{Node}, ma \textbf{non} da \code{Element}:
ha quindi \code{nodeName} e \code{childNodes}, ma non \code{tagName} né
\code{innerHTML}. Leggere su un oggetto una proprietà che non ha non è un
errore, in JavaScript: si ottiene semplicemente \code{undefined}. Lo vedremo
subito.

\section{Proprietà dei nodi}

\subsection{Nome e tipo}

\code{nodeName} e \code{tagName} danno informazioni sul tipo di un nodo. Sono in
sola lettura.

\begin{affianco}[0.6][c]
\begin{lstlisting}[style=html, name=nodename.html]
<body>
  <h1 id="h">Hello <em>DOM!</em></h1>
  <!-- commento -->
  <script>
    let body = document.body;
    console.log(body.firstChild.nodeName);          // #text
    console.log(body.firstChild.tagName);           // undefined
    console.log(body.childNodes[3].nodeName);       // #comment
    console.log(body.firstElementChild.nodeName);   // H1
    console.log(body.firstElementChild.tagName);    // H1
  </script>
</body>
\end{lstlisting}
\risultato
\begin{immagine}[\code{childNodes} di \code{body}: gli elementi\\
                 sono intervallati da nodi di testo.]
\begin{tikzpicture}

      \#text \textbackslash n/mtesto, \#comment/mcommento,
      \#text \textbackslash n/mtesto, SCRIPT/mdom} {
    \node[\st, anchor=west, minimum width=2.1cm] (n\i) at (0.9,-\i*0.6) {\t};
    \node[mindice, anchor=east] at (0.8,-\i*0.6) {[\i]};
  }
  \node[mnota, anchor=west] at ([xshift=4pt]n0.east) {\code{firstChild}};
  \node[mnota, anchor=west] at ([xshift=4pt]n1.east) {\code{firstElementChild}};
  \node[mnota, anchor=west] at ([xshift=4pt]n3.east) {\code{childNodes[3]}};
\end{tikzpicture}
\end{immagine}
\end{affianco}

Vediamo le stampe una per una.

\begin{itemize}
  \item \code{body.firstChild} è il nodo di testo che sta fra \tg{body} e
        \tg{h1}: contiene l'a-capo e i due spazi di indentazione,
        \code{"\textbackslash n\ \ "}. Il \code{nodeName} di un nodo di testo
        non è il suo contenuto: vale sempre \code{"\#text"}.
  \item Lo stesso nodo ha \code{tagName} uguale a \code{undefined}.
        \code{tagName} è una proprietà di \code{Element}, e un nodo di testo
        \textbf{non è un elemento}: non ha un tag, quindi non ha un nome di tag.
        Come visto nella gerarchia, leggere una proprietà che l'oggetto non ha
        restituisce \code{undefined}.
  \item \code{childNodes[3]} è il commento. Contando da zero: \code{[0]} il
        testo, \code{[1]} l'\tg{h1}, \code{[2]} il testo fra \tg{h1} e
        commento, \code{[3]} il commento, che ha \code{nodeName} uguale a
        \code{"\#comment"}.
  \item Per un elemento, \code{nodeName} e \code{tagName} coincidono: il nome
        del tag, in \textbf{maiuscolo} (\code{"H1"}) per i documenti HTML.
\end{itemize}

\begin{center}
\renewcommand{\arraystretch}{1.35}
\begin{tabular}{@{}l@{\hspace{1.2cm}}l@{\hspace{1.2cm}}l@{}}
  \textbf{Nodo} & \textbf{nodeName} & \textbf{tagName} \\
  elemento \tg{h1} & \code{"H1"}        & \code{"H1"} \\
  nodo di testo    & \code{"\#text"}     & \code{undefined} \\
  commento         & \code{"\#comment"}  & \code{undefined} \\
  \code{document}  & \code{"\#document"} & \code{undefined} \\
\end{tabular}
\end{center}

In sintesi: \code{nodeName} esiste per \textbf{ogni} nodo (è di \code{Node}),
\code{tagName} solo per gli elementi (è di \code{Element}).

\subsection{Attributi}

Quando il browser analizza un tag, per ogni attributo \textbf{standard} (cioè
previsto dalla specifica HTML per quel tipo di elemento: \attr{id},
\attr{class}, \attr{name}, \attr{value}, \attr{href}\ldots) crea una
\textbf{proprietà} corrispondente sull'oggetto DOM. Per gli attributi
\textbf{non standard}, inventati da noi come \attr{custom} qui sotto, non lo fa:
l'attributo resta scritto nell'HTML, ma sull'oggetto non c'è alcuna proprietà
con quel nome.

\begin{affianco}[0.6][c]
\begin{lstlisting}[style=html, name=attributi.html]
<body>
  <input id="x" class="inp ok" name="field" custom="y">
  <script>
    let i = document.body.firstElementChild;
    console.log(i.id);          // x
    console.log(i.classList);   // DOMTokenList ["inp", "ok"]
    console.log(i.name);        // field
    console.log(i.custom);      // undefined: custom non e' standard
    console.log(i.getAttribute("custom"));   // y
  </script>
</body>
\end{lstlisting}
\risultato
\begin{immagine}[Gli attributi standard diventano proprietà;\\
                 \code{custom} resta solo un attributo.]

\info{Per gli attributi non standard si usa getAttribute}{
  \code{getAttribute(nome)} legge il valore di \textbf{qualunque} attributo,
  standard o no, esattamente come è scritto nell'HTML; \code{setAttribute(nome,
  valore)} lo scrive e \code{removeAttribute(nome)} lo elimina. Attenzione a non
  confondere i due mondi: \code{i.custom = "z"} \textbf{non} modifica
  l'attributo, crea soltanto una normale proprietà JavaScript sull'oggetto, e
  \code{i.getAttribute("custom")} continua a restituire \code{"y"}.

  Per aggiungere dati propri a un elemento la specifica prevede gli attributi
  \code{data-*}, che il browser raccoglie nella proprietà \code{dataset}:
  \code{<div data-user-id="42">} si legge con \code{div.dataset.userId}. È il
  meccanismo che useremo nel capitolo sulle Single Page Application.}

Si noti anche che il nome della proprietà non è sempre uguale a quello
dell'attributo: all'attributo \attr{class} corrispondono \code{className} (la
stringa intera) e \code{classList} (la lista delle classi, con i metodi
\code{add} e \code{remove}), perché \code{class} è una parola riservata di
JavaScript.

Queste proprietà sono anche \textbf{scrivibili}:

    i.classList.remove("ok");
    i.classList.add("err");
    i.setAttribute("custom", "k");
    i.removeAttribute("name");
  </script>
</body>

<!-- l'input dopo l'esecuzione dello script -->
<input id="w" class="inp err" custom="k">
\end{lstlisting}
\risultato

\subsection{innerHTML e outerHTML}

\begin{affianco}[0.5][c]
\begin{itemize}
  \item \code{innerHTML} è il codice HTML \textbf{contenuto} nell'elemento: tutto
        quello che sta fra il tag di apertura e quello di chiusura (riquadro
        blu).
  \item \code{outerHTML} è il codice HTML \textbf{dell'intero} elemento, tag di
        apertura e di chiusura compresi (riquadro arancione).
\end{itemize}
\risultato

\begin{lstlisting}[style=html, name=innerhtml.html]
<body>
  <h1 id="h">Hello <em>DOM!</em></h1>
  <script>
    let body = document.body;
    console.log(body.firstElementChild.innerHTML);  // Hello <em>DOM!</em>
    console.log(body.firstChild.innerHTML);         // undefined (non e' un HTMLElement)
    console.log(body.firstElementChild.outerHTML);  // <h1 id="h">Hello <em>DOM!</em></h1>
  </script>
</body>

La seconda riga stampa \code{undefined} per lo stesso motivo visto con
\code{tagName}: \code{body.firstChild} è il nodo di testo
\code{"\textbackslash n\ \ "}, che non è un elemento e quindi non ha
\code{innerHTML}.

La cosa interessante è che entrambe le proprietà sono \textbf{scrivibili}:
assegnando loro un nuovo valore si cambia il contenuto della pagina.
Assegnare \code{innerHTML} sostituisce il riquadro blu (il contenuto), mentre
assegnare \code{outerHTML} sostituisce il riquadro arancione, cioè
\textbf{l'elemento intero}.

\begin{affianco}[0.58][c]
\begin{lstlisting}[style=html, name=innerhtml-scrittura.html]
<body>
  <h1 id="h">Hello <em>DOM!</em></h1>
  <script>
    let elem = document.body.firstElementChild;

    elem.innerHTML = "DOM: <em>Wow!</em>";
    // cambiato il contenuto dell'elemento <h1>

    elem.outerHTML = `<p>${elem.innerHTML}</p>`;
    // ora l'<h1> e' diventato un <p>, con lo stesso contenuto
  </script>
</body>
\end{lstlisting}
\risultato
\begin{browser}[all'inizio]
  {\Lora\bfseries\Huge Hello \textit{DOM!}}
\end{browser}
\begin{browser}[dopo innerHTML]
  {\Lora\bfseries\Huge DOM: \textit{Wow!}}
\end{browser}
\begin{browser}[dopo outerHTML]
  DOM: \textit{Wow!}
\end{browser}
\wtnota{L'ultimo è un paragrafo: niente più stile da titolo.}
\end{affianco}

Nell'ultima assegnazione il template letterale usa \code{elem.innerHTML}, cioè
solo il contenuto del titolo: il nuovo \tg{p} prende il posto dell'\tg{h1} e ne
eredita il testo. Che cosa succederebbe con \code{elem.outerHTML}?

\begin{affianco}[0.48][c]
\begin{lstlisting}[style=js, name=variante.js]
elem.innerHTML = "DOM: <em>Wow!</em>";

elem.outerHTML = `<p>${elem.outerHTML}</p>`;
\end{lstlisting}
\begin{lstlisting}[style=html, name=DOM risultante]
<p></p>
<h1 id="h">DOM: <em>Wow!</em></h1>
<p></p>
\end{lstlisting}

Il testo assegnato sarebbe un \tg{p} che contiene l'intero \tg{h1}. Ma in HTML
un paragrafo può contenere solo testo ed elementi \guillemotleft di
riga\guillemotright\ come \tg{em} o \tg{a}, non un titolo. Il parser, quando
incontra \tg{h1} con un \tg{p} ancora aperto, \textbf{chiude automaticamente} il
paragrafo; poi la \code{</p>} finale non ha più un paragrafo da chiudere, e il
parser ne crea un altro, vuoto. Il risultato è un titolo identico a prima,
circondato da due paragrafi vuoti: nel browser non cambia nulla di visibile.
È un buon esempio di una regola generale: assegnando \code{innerHTML} o
\code{outerHTML} non si scrive il DOM direttamente, si passa del codice HTML al
parser, che lo interpreta (e corregge) come farebbe con un file.

\error{innerHTML e input dell'utente}{
  Assegnare a \code{innerHTML} una stringa che contiene, anche solo in parte,
  dati forniti dall'utente è il modo classico di aprire una vulnerabilità di
  tipo \textit{Cross-Site Scripting} (XSS): il browser interpreta come markup
  ciò che gli si passa, quindi anche eventuali tag \tg{script} o attributi
  \code{onerror}. Quando serve inserire solo testo si usa \code{textContent} o
  \code{innerText}, che non interpretano nulla. Torneremo sull'argomento nel
  capitolo sulla sicurezza.}

\section{Modificare la struttura del DOM}

Non siamo limitati a modificare gli elementi esistenti: possiamo creare
dinamicamente nuovi elementi, rimuoverne di esistenti e cambiare la struttura
dell'albero. È la chiave per costruire pagine \guillemotleft vive\guillemotright\ e reattive.

Per aggiungere qualcosa alla pagina bisogna rispondere a due domande, e conviene
farlo in quest'ordine:

\begin{enumerate}
  \item \textbf{dove} va messo il nuovo contenuto, rispetto a un elemento che già
        esiste: dentro (all'inizio o in fondo) oppure accanto (prima o dopo)?
  \item \textbf{come} si crea il nuovo nodo?
\end{enumerate}

\subsection{Dove: i quattro punti di inserimento}

Ogni nodo offre quattro metodi per inserire contenuto in una posizione precisa
\textbf{rispetto a sé stesso}. Tutti accettano uno o più nodi, oppure delle
stringhe (che vengono inserite come testo).

\subsection{Come: creare i nodi}

Un nuovo elemento si crea con \codel{document.createElement(tag)}, un nuovo nodo
di testo con \codel{document.createTextNode(testo)}.

Il punto da capire bene è che \code{createElement} \textbf{crea} l'elemento ma
\textbf{non lo aggiunge alla pagina}. Il nuovo oggetto esiste solo in memoria,
nella variabile che lo contiene: il browser non lo mostra, perché non sa ancora
dove dovrebbe stare. È come un foglio già scritto ma non ancora appeso alla
bacheca. Per farlo comparire bisogna dire \textbf{dove} metterlo, con uno dei
quattro metodi appena visti.

\begin{affianco}[0.52][c]
\codicepiccolo
\begin{lstlisting}[style=html, name=crea.html]
<body>
  <script>
    let heading = document.createElement("h1");  // 1
    // il nuovo <h1> non e' ancora nel DOM

    let title = document.createTextNode("Wow!"); // 1
    // nemmeno il nodo di testo e' ancora nel DOM

    heading.append(title);           // 2: il testo nell'<h1>
    document.body.prepend(heading);  // 3: l'<h1> in cima al <body>
  </script>
</body>
\end{lstlisting}
\risultato
\begin{immagine}[A sinistra il DOM della pagina, a destra i nodi\\
                 che esistono solo in memoria.]

\section{Eventi}

\dfn{Evento}{
  Un \term{evento} è un segnale che qualcosa è accaduto.}

Gli eventi possono riguardare:

\begin{itemize}

\end{itemize}

\subsection{Gestori di eventi}

Per reagire agli eventi si definiscono funzioni \term{gestore}
(\textit{handler}), eseguite quando l'evento scatta.

Il modo più semplice è usare gli attributi HTML \code{on<evento>}, il cui valore
è il codice JavaScript da eseguire.

\begin{affianco}[0.6][c]
\begin{lstlisting}[style=html, name=handler-attributo.html]
<input type="button" value="Click me" onclick="handleClick();">
<script>
  function handleClick() {
    console.log("Click handled");
  }
</script>
\end{lstlisting}
\risultato
\begin{browser}[handler.html]
  \wtbottone{Click me}
\end{browser}

\end{console}
\end{affianco}

I gestori si possono anche definire dinamicamente da JavaScript, scrivendo la

\info{Perché addEventListener è preferibile}{
  La proprietà \code{on<evento>} può contenere \textbf{un solo} gestore:
  assegnarne un altro cancella il precedente.
  \code{addEventListener} permette invece di registrare quanti gestori si
  vogliono per lo stesso evento, e di rimuoverli selettivamente con
  \code{removeEventListener}. In un'applicazione reale, dove parti diverse del
  codice possono voler reagire allo stesso evento, è l'unica scelta sensata.}

\subsection{Evento e funzione gestore: chi chiama chi}

È facile confondere l'evento con la funzione che lo gestisce, ma sono due cose
diverse.

\begin{itemize}
  \item L'\textbf{evento} (per esempio \code{"click"}) è un \textbf{fatto}:
        qualcosa è successo. Lo produce il browser, quando succede: non sappiamo
        in anticipo se e quante volte l'utente farà clic.
  \item Il \textbf{gestore} (per esempio \code{handleClick}) è una normale
        \textbf{funzione}, scritta da noi, che dice \textbf{che cosa fare}
        quando quel fatto accade.
\end{itemize}

Registrare un gestore significa dire al browser: \guillemotleft quando succede
\textit{questo evento} su \textit{questo elemento}, chiama \textit{questa
funzione}\guillemotright. Non siamo noi a chiamarla: la chiama il browser, al
momento giusto, ogni volta che l'evento si ripete, passandole l'oggetto evento.

\begin{affianco}[0.54][c]
\codicepiccolo
\begin{lstlisting}[style=html, name=chiamare-o-registrare.html]
<button>Salutami</button>
<script>
  let btn = document.querySelector("button");
  function saluta() { console.log("Ciao!"); }

  saluta();                                 // chiamata: subito
  btn.addEventListener("click", saluta);    // registrazione
  btn.addEventListener("click", saluta());  // ERRORE tipico
</script>
\end{lstlisting}
\begin{console}[Console: caricamento, poi un clic]
Ciao!        <- saluta(), riga 6
Ciao!        <- saluta(), riga 8
Ciao!        <- il clic: solo la riga 7
\end{console}
\risultato
\begin{immagine}[Prima registrare, poi è il browser a chiamare,\\
                 una volta per ogni clic.]
\begin{tikzpicture}[
    a/.style={-{Stealth[length=5pt,width=4pt]}, line width=0.8pt,
      draw=neutral!45!black},
    ev/.style={circle, fill=accent!70!black, inner sep=2pt},
    lab/.style={font=\Lato\scriptsize, align=center}]
  \draw[a] (0,0) -- (6.6,0) node[mnota, right]{tempo};
  \node[mfun, anchor=south] at (0.6,0.25) {addEventListener};
  \draw[neutral!45!black] (0.6,0.25) -- (0.6,-0.1);
  \node[lab, anchor=north] at (0.6,-0.2) {caricamento:\\registrazione};
  \foreach \x/\n in {3.3/1, 5.5/2} {
    \node[ev] at (\x,0) {};
    \node[lab, anchor=south] at (\x,0.2) {clic \n};
    \node[mcod, anchor=north, text=accent!75!black] at (\x,-0.2) {saluta(event)};
  }
  \node[lab, text=neutral!45!black, anchor=north] at (4.4,-0.75)
    {chiamate fatte dal browser};
\end{tikzpicture}
\end{immagine}
\end{affianco}

L'ultima riga è un errore molto comune: con le parentesi, \code{saluta()}
viene \textbf{eseguita subito}, durante il caricamento, e ad
\code{addEventListener} arriva il suo valore di ritorno, \code{undefined}.
Nessuna funzione viene registrata, e i clic non la eseguono. Per registrare un
gestore si passa la funzione \textbf{senza} parentesi: il nome della funzione,
non il risultato della sua chiamata.

Quando usare l'una o l'altra cosa, quindi:

\begin{itemize}
  \item si \textbf{chiama} direttamente una funzione (\code{saluta()}) quando
        l'azione va fatta \textbf{adesso}, una volta, mentre lo script viene
        eseguito;
  \item la si \textbf{registra} come gestore (\code{addEventListener("click",
        saluta)}) quando l'azione deve avvenire \textbf{in risposta} a
        qualcosa che non è ancora successo, e non sappiamo quando (o se)
        succederà.
\end{itemize}

Lo stesso ragionamento spiega le parentesi nei tre modi di definire un gestore:

\begin{center}
\renewcommand{\arraystretch}{1.45}
\begin{tabular}{@{}l@{\hspace{0.6cm}}>{\raggedright\arraybackslash}p{3.2cm}@{\hspace{0.5cm}}>{\raggedright\arraybackslash}p{4.2cm}@{\hspace{0.5cm}}l@{}}
  \textbf{Modo} & \textbf{Si scrive} & \textbf{Parentesi?} & \textbf{Gestori} \\
  \code{onclick="saluta()"} & codice JavaScript, come stringa
    & \textbf{sì}: è il codice da eseguire al clic & uno \\
  \code{btn.onclick = saluta} & una funzione
    & \textbf{no}: si assegna la funzione & uno \\
  \code{btn.addEventListener("click", saluta)} & una funzione
    & \textbf{no}: si passa la funzione & quanti si vuole \\
\end{tabular}
\end{center}

\subsection{Il valore di this in un gestore}

Dentro un gestore, \code{this} vale l'elemento a cui il gestore è stato
assegnato.

\subsection{L'oggetto evento}

Per gestire bene un evento servono spesso dettagli: in un \code{keydown}, quale
tasto è stato premuto? In un \code{click}, a quali coordinate? L'utente teneva
premuto \code{CTRL}?

Tutti i dettagli sono forniti in un \term{oggetto evento}, passato
automaticamente ai gestori. Tipi di evento diversi hanno proprietà diverse: per
esempio gli eventi da tastiera hanno una proprietà \code{key} che rappresenta il
tasto premuto.

\begin{affianco}[0.62][c]
\begin{lstlisting}[style=html, name=oggetto-evento.html]
<input type="text" placeholder="Write here" autofocus>
<script>
  function handler(event) {
    console.log(`You pressed ${event.key}`);
  }

  document.querySelector("input").addEventListener("keyup", handler);
</script>
\end{lstlisting}
\risultato
\begin{browser}[evento.html]
  \wtcampo[4cm][white]{JS\textbar}
\end{browser}
\begin{console}[Console, digitando J e poi S]
You pressed J
You pressed S
\end{console}
\end{affianco}

\section{Propagazione degli eventi}

\subsection{Bubbling}

\dfn{Event bubbling}{
  Quando un evento scatta su un elemento, vengono eseguiti prima tutti i gestori
  registrati su quell'elemento, poi tutti quelli registrati sul suo genitore, e
  così via risalendo fino alla radice del DOM. Questo meccanismo si chiama
  \term{event bubbling} (\guillemotleft ribollimento\guillemotright).}

Si applica alla maggior parte degli eventi, ma non a tutti: gli eventi di
\code{focus}, per esempio, non fanno bubbling.

\begin{esempio}{Il percorso di un clic}
Ogni elemento del documento ha un gestore. Facendo clic sul \tg{p}, i gestori
vengono eseguiti risalendo l'albero (a destra, nell'ordine numerato), e la
console mostra le quattro righe:

\begin{affianco}[0.55][c]
\begin{lstlisting}[style=html, name=bubbling.html]
<body>
  <section onclick="console.log('section');">
    <article onclick="console.log('article');">
      <p onclick="console.log('p');">Bubbling</p>
    </article>
  </section>
  <script>
    document.onclick = () => console.log("document");
  </script>
</body>
\end{lstlisting}
\risultato

\subsection{Delegazione degli eventi}

La \term{delegazione degli eventi} è un pattern potente: se molti elementi
possono generare eventi simili, invece di assegnare un gestore a ciascuno se ne
usa \textbf{uno solo} sul loro antenato comune. Gli elementi
\guillemotleft delegano\guillemotright\ la gestione all'antenato.

La proprietà \code{target} dell'oggetto evento permette di sapere su quale
elemento l'evento è stato effettivamente generato.

\begin{esempio}{Un solo gestore per tutta la tabella}
\begin{affianco}[0.58][c]
\begin{lstlisting}[style=html, name=delegazione.html]
<table onclick="handler(event);">
  <tr><th>Col</th><th>Col</th></tr>
  <tr><td>1</td><td>2</td></tr>
  <tr><td>3</td><td>4</td></tr>
  <tr><td>5</td><td>6</td></tr>
</table>
<script>
  function handler(event) {
    if (event.target.nodeName === "TD") {
      let oldValue = parseInt(event.target.innerHTML);
      event.target.innerHTML = ++oldValue;
    }
  }
</script>
\end{lstlisting}
\risultato
\begin{browser}[delegazione.html]
  \renewcommand{\arraystretch}{1.25}%
  \begin{tabular}{|c|c|}
    \hline \textbf{Col} & \textbf{Col} \\
    \hline 1 & \colorbox{accent!18!white}{3} \\
    \hline 3 & 4 \\
    \hline 5 & 6 \\ \hline
  \end{tabular}
\end{browser}
\wtnota{Dopo un clic sul 2, la cella vale 3.\\
        \code{event.target} è la \code{<td>},\\ il gestore è sulla \code{<table>}.}
\end{affianco}

Un solo gestore serve sei celle. Il vantaggio non è solo la brevità: se in
seguito si aggiungessero righe alla tabella \textbf{dinamicamente}, queste
funzionerebbero subito, senza bisogno di registrare nuovi gestori.
\end{esempio}

\subsection{Fermare il bubbling}

Un gestore può decidere che l'evento è stato completamente elaborato e che non
serve propagarlo oltre, invocando il metodo \code{stopPropagation()}
sull'oggetto evento.

\begin{affianco}[0.55][c]
\begin{lstlisting}[style=html, name=stop-propagation.html]
<body>
  <section onclick="console.log('section');">
    <article>
      <p onclick="console.log('p');">Bubbling</p>
    </article>
  </section>
  <script>
    let art = document.querySelector("article");
    art.addEventListener("click", handler);

    function handler(event) {
      console.log(this.tagName);
      event.stopPropagation();   // non arriva a <section>
    }
  </script>
</body>
\end{lstlisting}
\risultato
\begin{immagine}

\warning{Fermare la propagazione con parsimonia}{
  La regola pratica è di \textbf{non} fermare la propagazione a meno di avere
  una buona ragione. Un antenato potrebbe aver bisogno di intercettare
  quell'evento, oggi o in futuro: sistemi di analisi, chiusura automatica dei
  menu a comparsa e molte librerie si basano proprio sul fatto che gli eventi
  risalgano fino in cima.}

\subsection{Generare eventi da JavaScript}

Da JavaScript è anche possibile \textbf{generare} eventi. La proprietà
\code{isTrusted} vale \code{false} per gli eventi artificiali.

\begin{affianco}[0.6][c]
\begin{lstlisting}[style=html, name=dispatch.html]
<input type="button" value="Click me">
<script>
  function handler(event) {
    console.log(`${event.type} event. Trusted: ${event.isTrusted}`);
  }

  let input = document.querySelector("input");
  input.onclick = handler;

  let click = new Event("click");
  input.dispatchEvent(click);   // isTrusted vale false
</script>
\end{lstlisting}
\risultato
\begin{console}[Console, al caricamento]
click event. Trusted: false
\end{console}
\wtnota{Un clic vero darebbe invece\\ \code{Trusted: true}.}
\end{affianco}

\section{Ordine di esecuzione degli script}

Man mano che i nostri script diventano più complessi, interagiscono con il DOM e
registrano gestori, dobbiamo sapere \textbf{quando} il codice viene eseguito
durante il caricamento di una pagina.

\begin{itemize}
  \item In generale, gli script vengono scaricati ed eseguiti \textbf{nell'ordine
        in cui compaiono}, mentre l'analisi della pagina è \textbf{sospesa}.
  \item Gli script esterni con l'attributo \attr{defer} vengono scaricati
        \textbf{in parallelo} ed eseguiti \textbf{dopo} che la pagina è stata
        completamente analizzata.
  \item Gli script esterni con l'attributo \attr{async} vengono scaricati in
        parallelo ed eseguiti \textbf{appena sono pronti}.
  \item Gli script di tipo modulo si comportano come \attr{defer} per
        impostazione predefinita, e possono essere dichiarati \attr{async}.
\end{itemize}

\begin{esempio}{Perché l'ordine conta}
Consideriamo lo script \code{load.js} (a sinistra), che cerca un \tg{h1} nel
\tg{body}, e la pagina che lo include nell'\tg{head} (a destra):

\begin{affianco}[0.45]
\begin{lstlisting}[style=js, name=load.js]
let h1 = document.body.querySelector("h1");
console.log(h1.innerText);
\end{lstlisting}
\risultato
\begin{lstlisting}[style=html, name=pagina.html]
<!DOCTYPE html>
<html>
  <head>
    <meta charset="utf-8">
    <title>Events</title>
    <script src="load.js"></script>
  </head>
  <body>
    <h1>JavaScript</h1>
  </body>
</html>
\end{lstlisting}
\end{affianco}

Che cosa compare in console dipende da \textbf{come} lo script è incluso.

\begin{affianco}[0.45][c]
\begin{lstlisting}[style=html]
<script src="load.js"></script>
\end{lstlisting}
\risultato
\begin{console}
Uncaught TypeError: document.body is null
\end{console}
\end{affianco}

Lo script viene eseguito appena il parser lo incontra, nell'\tg{head}: il
\tg{body} non è ancora stato creato, quindi \code{document.body} vale
\code{null}, e chiamare un metodo su \code{null} genera un \code{TypeError}
(Chrome lo scrive come \textit{Cannot read properties of null}).

\begin{affianco}[0.45][c]
\begin{lstlisting}[style=html]
<script defer src="load.js"></script>
\end{lstlisting}
\risultato
\begin{console}
JavaScript
\end{console}
\end{affianco}

Con \attr{defer} lo script viene eseguito dopo l'analisi completa della pagina,
quando l'\tg{h1} esiste.

\begin{affianco}[0.45][c]
\begin{lstlisting}[style=html]
<script async src="load.js"></script>
\end{lstlisting}
\risultato
\begin{immagine}
\tikz\node[fill=orange-gradient-6, text=white, rounded corners=3pt, inner sep=6pt,
  text width=7.2cm, align=center, font=\Lato\small]
  {Non si può sapere con certezza: dipende da quanto tempo serve a scaricare
   lo script.};
\end{immagine}
\end{affianco}

L'alternativa che funziona sempre, indipendentemente da dove si trova il tag, è
attendere l'evento \code{DOMContentLoaded}:

\begin{affianco}[0.6][c]
\begin{lstlisting}[style=js, name=load.js]
document.addEventListener("DOMContentLoaded", () => {
  let h1 = document.body.querySelector("h1");
  console.log(h1.innerText);
});
\end{lstlisting}
\risultato
\begin{console}
JavaScript
\end{console}
\end{affianco}
\end{esempio}
